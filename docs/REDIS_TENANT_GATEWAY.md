# Redis tenant gateway

Proxima's Redis integration is a restricted RESP2 TLS gateway. It authenticates a client username/password against a local identity registry, binds the connection to one tenant, derives an opaque key prefix, rewrites every supported key argument, and authenticates upstream as that tenant's Redis ACL user. Client connections and upstream Redis connections both use TLS; upstream certificates are verified against the configured CA.

## Identity registry

Create secrets/redis-identities.json with one record per client principal:

    {
      "users": [
        {
          "username": "tenant_a_client",
          "tenant_id": "tenant-a",
          "client_password_sha256": "64-character-hex-sha256-of-client-password",
          "upstream_username": "proxima_tenant_a",
          "upstream_password": "secret-from-your-secret-manager"
        }
      ]
    }

The gateway accepts either AUTH password (registry username default) or AUTH username password. Use named principals. The registry is loaded at process start; rotate credentials by updating the secret and restarting the gateway. Store the file as a Docker secret with restrictive host permissions. The SHA-256 client verifier is not a password-storage substitute for a strong randomly generated client secret.

## Upstream Redis ACL

Create one ACL user per tenant. Its key pattern must match only the namespace derived by Proxima for that tenant, and its command allowlist must be no broader than the gateway's supported commands. Example command shape (replace the namespace with the exact prefix generated by the gateway and use a strong secret):

    ACL SETUSER proxima_tenant_a on >UPSTREAM_SECRET ~proxima:{TENANT_HASH}:* +get +set +del +exists +mget +mset +incr +expire +ttl +type +bitop

The ACL pattern is a second enforcement layer. Do not grant +@all, administrative categories, scripting, Pub/Sub, transactions, keyspace-wide scans, or keyless commands that expose server-wide state. Logical database numbers are not a security boundary.

## Supported protocol and commands

- RESP2 arrays of bulk strings only; inline protocol and RESP3 are rejected.
- Client AUTH is required before any data command.
- PING and QUIT are handled by the gateway.
- The current command allowlist is intentionally narrow: common string, hash, list, set, sorted-set, expiry, selected stream, and multi-key operations enumerated in redis_protocol.rs.
- Unknown commands and malformed/oversized frames fail closed.
- Transactions, Lua/functions, Pub/Sub, cluster administration, key scans, and server administration are unsupported.

Check the allowlist in source before enabling a workload. Redis command key positions are command-specific; do not add a command without validating all optional and variadic key arguments against the Redis command specification and adding adversarial tests.

## Customer deployment

The opt-in Compose profile is redis. Configure the upstream Redis address, upstream TLS DNS name and CA file, gateway TLS certificate/key, and identity registry files under secrets/. Start it with:

    docker compose -f compose.customer.yaml --profile redis up -d redis-gateway

The default bind is loopback-only. Set PROXIMA_REDIS_BIND_ADDRESS only when an externally reachable listener is required and protected by network controls. The gateway requires upstream TLS and has a bounded connection count. It does not yet support dynamic identity reload, RESP3, command cancellation, or transparent compatibility with arbitrary Redis clients; clients must stay within the documented RESP2 and command surface.

## Verification

scripts/test-redis-tenant-gateway-ci.sh starts a disposable Redis 7.4 TLS server with separate ACL users, starts the gateway with a two-principal identity registry, and verifies overlapping keys remain isolated, multi-key operations are namespaced, invalid credentials fail, and FLUSHALL is denied.
