# Proxima Engine — Provider Implementation Status

This matrix separates code present in the repository from runtime activation, provider-side provisioning, protocol coverage and real-provider acceptance. A provider must not be described as production-ready solely because a policy builder, SQL script or helper module exists.

## Runtime acknowledgement semantics

- `staged` means the signed configuration bundle and encrypted credential envelope were accepted and desired state was persisted. It is not a healthy runtime claim.
- `applied` is emitted only for a provider path that has actually activated its runtime and passed its configured health checks.
- `failed` means an attempted supported activation failed. The Engine records a bounded error code and does not report the assignment as healthy.
- A node-level applied acknowledgement does not by itself prove every tenant binding's isolation. Tenant-binding activation must remain gated on provider-specific identity and isolation evidence.
- The Engine now treats omission from the latest authenticated Cloud desired-state bundle (including an empty bundle) as revocation for persisted assignments. For MySQL/MariaDB, MongoDB and Redis it stops the corresponding supervised gateway and deletes the node-local gateway identity registry before marking the durable assignment record revoked. This revokes local gateway state; it does not delete upstream database users/ACLs or remote cloud identities.
- Authenticated Cloud reconciliation now invokes the MySQL/MariaDB, MongoDB and Redis runtime activation modules and sends `applied` only after each activation path reports success. Preview assignments remain `staged`; failed activation is acknowledged as `failed`. Runtime modules are exported by the Engine crate so their code and tests are included in workspace builds.
- DynamoDB IAM, Cassandra CQL, Oracle TNS and SQL Server native lifecycle executors are now concrete provider clients, but they are not yet called by the Cloud assignment worker. Search role/user APIs are implemented in the native REST client, including OpenSearch backend-role mapping and tenant-authentication verification, but are not yet called by the Cloud assignment worker.

## Build and acceptance evidence

The Windows baseline run on 2026-11-23 reported:

- `cargo check --workspace --all-targets`: PASS.
- The earlier Windows baseline run reported 164 library tests PASS and 19 Engine binary tests PASS. After exporting the runtime modules and wiring Cloud assignment activation, rerun the full build and unit suites; the new provider SDK dependencies also require Cargo to refresh `Cargo.lock`.
- MySQL, MariaDB and MongoDB real-service integration tests were ignored because their disposable services were not running. Redis real-server adversarial acceptance was not run.
- The PostgreSQL integration test failed to connect (`WSAECONNREFUSED` / OS error 10061) at its configured address. This is an environment/service availability failure, not a Rust compilation failure, and it is not a passing provider acceptance result.

A successful workspace build and unit suite are not equivalent to twelve-provider production acceptance. Use `scripts/verify-provider-matrix.ps1` for a Windows-side build/unit summary and explicit SKIP/NOT_IMPLEMENTED reporting; use the provider-specific scripts and the consolidated verification requirements in [Database Production Verification](DATABASE_PRODUCTION_VERIFICATION.md) for real-server evidence.
